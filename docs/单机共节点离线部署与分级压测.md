# 单机共节点：在线打包、离线部署与分级压测

适用于 Linux x86_64，推理服务与压测/观测链路在同一台 GPU/DCU 节点。推理服务、模型权重、设备驱动和 GPU 容器运行时须提前部署；本工具部署 Prometheus、Grafana、Loki、Alloy、Exporter、日志轮转及 AISBench 客户端。在线机无需 GPU，其模拟冒烟验证软件链路；离线机再验证真实服务。

## 1. 在线机一键构建交付包

准备 Git、可访问的 Docker daemon、Python 3.10+（含 venv/pip）、GNU tar/coreutils，以及足够的构建/镜像导出磁盘空间（建议至少 30 GB）。网络须可访问 GitHub、镜像源、PyPI、AISBench 构建所用的 Debian/PyTorch 等依赖源；私有镜像先完成 `docker login`。

在已有仓库根目录运行（脚本会另建目录重新拉取远端，**只打包远端已提交的版本**）：

```bash
REF=main OFFLINE_PYTHON=3.11 \
  bash scripts/build_offline_bundle.sh
```

默认拉取当前项目远端 `https://github.com/shangbinbin/LLM-Inference-Benchmark.git`。自建镜像仓库或不同交付选择可先修改一份 YAML，然后指定绝对路径：

```bash
REPO_URL=https://github.com/shangbinbin/LLM-Inference-Benchmark.git \
REF=main OFFLINE_PYTHON=3.11 \
SITE_CONFIG=/opt/build/site.yaml \
DELIVERY_CONFIG=/opt/build/offline-images.yaml \
TOKENIZER_DIR=/opt/models/Qwen3-0.6B \
OUTPUT_DIR=/opt/delivery \
  bash scripts/build_offline_bundle.sh
```

后三个配置变量均可省略；默认现场模板为 [`single-node.example.yaml`](../configs/sites/single-node.example.yaml)，默认交付 NVIDIA/DCU 两种 Exporter。`TOKENIZER_DIR` 仅复制 tokenizer 相关文件，不包含权重；省略时在离线机准备实际 tokenizer。`OFFLINE_PYTHON` 必须与离线机的 CPython 主次版本一致；包内带相应 Linux x86_64 wheel，无需离线下载依赖。默认 Python 3.11，支持设置为其他有 PyYAML wheel 的版本。海光私有镜像不可访问时，可在 `delivery.yaml` 的 `selected_gpu_exporters` 中仅保留实际需要的厂商；离线 `gpu.vendor` 应与交付选择一致。

自动执行：远端拉取并记录提交 → 准备 Python 依赖和离线 wheel → 单元测试 → 构建 toolbox/AISBench → 拉取并校验镜像架构、导出镜像 → 用这些镜像进行 CPU 模拟冒烟 → 验证请求结果、Prometheus、Grafana 和 Loki → 关闭模拟栈 → 打包源码、镜像、wheel、配置及验证证据。冒烟默认使用 43000 起的七个端口，冲突时设置 `SMOKE_PORT_BASE`。任一步失败返回非零，保留 `.build-*/build.log` 和诊断数据，不产出成功压缩包。

输出为 `generated/delivery/llm-bench-offline-<提交>-<UTC时间>.tar.gz` 及 `.sha256`。包内有 `repo/`、`images/`、`wheelhouse/`、`metadata/`、带注释的 `site.yaml`、`delivery.yaml`、`SHA256SUMS` 和本文。模拟冒烟结果在 `metadata/online-smoke.json`，对应配置在 `metadata/online-smoke.yaml`，源提交在 `metadata/revision.txt`。不要从构建中的 `.build-*` 目录提前拷包。

### 1.1 在线无 GPU 服务器使用下载的 tokenizer 模拟压测

本步骤适用于在线 Linux x86_64 CPU 服务器，使用真实模型的 tokenizer 生成输入，向仓库自带的 `fixture` 模拟接口发起请求。无需 GPU、设备驱动、模型权重或真实推理服务；模拟 GPU 指标和响应由 fixture 提供，结果用于验证客户端、tokenizer、指标与日志链路，不能作为真实模型性能或容量结论。

以下命令均在**在线机仓库根目录**执行。使用独立的虚拟环境和模拟配置，不修改离线现场的 `site.yaml`。

**准备工具和 tokenizer。** 如果已经下载 tokenizer，将 `CPU_TOKENIZER_DIR` 改为实际绝对路径，并跳过下面的 ModelScope 下载代码块。

```bash
python3 -m venv generated/cpu-tokenizer-tools
source generated/cpu-tokenizer-tools/bin/activate
python -m pip install -r requirements.txt
export PATH="$PWD/bin:$PATH"
export CPU_TOKENIZER_DIR="$PWD/generated/tokenizers/Qwen3-0.6B"
```

尚未下载时，以 Qwen3-0.6B 为例，只下载 tokenizer/config 文件：

```bash
python -m pip install modelscope
python - <<'PY'
import os
from pathlib import Path
from modelscope.hub.snapshot_download import snapshot_download

target = Path(os.environ['CPU_TOKENIZER_DIR']).resolve()
snapshot_download(
    model_id='Qwen/Qwen3-0.6B', revision='master', local_dir=str(target),
    allow_file_pattern=[
        'tokenizer*', 'vocab.json', 'merges.txt', 'special_tokens_map.json',
        'added_tokens.json', 'config.json', 'chat_template*',
    ],
)
for name in ('tokenizer_config.json', 'tokenizer.json'):
    if not (target / name).is_file():
        raise RuntimeError('Missing tokenizer file: ' + name)
print('Tokenizer directory:', target)
PY
```

下载需要可达的 PyPI 和 ModelScope 文件服务；可按在线机网络选择 pip 镜像源。`master` 会变化，需要复现时固定为已记录的模型提交或标签。已有目录应包含该模型完整的词表、配置和模板；避免混入其他模型文件。此处不安装主机 PyTorch，也不下载模型权重。

**生成独立模拟配置。** 运行配置启用本地镜像模式；额外生成的 build 配置仅用于在线构建镜像。已有配置时脚本拒绝覆盖，重复测试可直接复用。

```bash
export CPU_CONFIG="$PWD/generated/online-cpu-smoke.yaml"
export CPU_BUILD_CONFIG="$PWD/generated/online-cpu-smoke-build.yaml"
python - <<'PY'
import os
import sys
from pathlib import Path
sys.path.insert(0, 'scripts')
from config_io import read_object, write_yaml

tokenizer = Path(os.environ['CPU_TOKENIZER_DIR']).resolve()
if not (tokenizer / 'tokenizer_config.json').is_file():
    raise RuntimeError('Check CPU_TOKENIZER_DIR: ' + str(tokenizer))
cfg = read_object('configs/stacks/nerdctl-offline-smoke.yaml')
cfg.update(project='llm-bench-online-cpu', task='online-cpu-smoke',
           simulation=True, platform='linux/amd64', runtime=['docker'],
           host_metrics='container', offline=True)
cfg['storage'].update(root='generated/online-cpu-smoke',
                      logs='generated/online-cpu-smoke-logs', tokenizer=str(tokenizer))
cfg['inference'].update(base_url='http://fixture:18000/', model='mock-model', api='completions')
cfg['gpu']['vendor'] = 'nvidia'
cfg['ports'] = {'grafana':33005, 'prometheus':39095, 'loki':33105, 'alloy':32350,
                'node-exporter':39105, 'gpu-exporter':39405, 'fixture':38085}
cfg['benchmark'].update(dataset_type='tokenid', prefix_length=0,
                        input_length=64, output_length=16, request_count=8,
                        concurrency=2, request_rate=0, warmups=0, retry=1, mode='perf')
outputs = {Path(os.environ['CPU_CONFIG']): cfg,
           Path(os.environ['CPU_BUILD_CONFIG']): {**cfg, 'offline': False}}
for path in outputs:
    if path.exists():
        raise FileExistsError('Reuse or review the existing config: ' + str(path))
for path, value in outputs.items():
    write_yaml(path, value)
PY
```

保留 `simulation: true`、`host_metrics: container`、`fixture` 地址和 `mock-model`。`gpu.vendor: nvidia` 在这里仅选择模拟指标，不会启动真实 DCGM Exporter，也不会要求 NVIDIA GPU。更换 tokenizer 不代表加载了该模型。上述端口须空闲；如冲突，在启动前同时调整两份模拟配置的 `ports`。有代理时，让容器间的 `fixture`、`node-exporter`、`loki`、`alloy`、`prometheus`、`grafana` 等服务名绕过外部代理。

**准备镜像并验证 tokenizer 本地加载。** 已完成第 1 节且本机镜像齐全时，可跳过以下构建/拉取代码块；单独做 CPU 模拟时，只需构建两个项目镜像并准备五个观测镜像，不必拉取设备 Exporter：

```bash
llm-bench images build --config "$CPU_BUILD_CONFIG"
python - "$CPU_CONFIG" <<'PY'
import subprocess
import sys
from pathlib import Path
sys.path.insert(0, 'scripts')
from config_io import read_object

cfg = read_object(Path(sys.argv[1]))
for role in ('prometheus', 'grafana', 'loki', 'alloy', 'node-exporter'):
    subprocess.run(['docker', 'pull', '--platform', cfg['platform'], cfg['images'][role]], check=True)
PY
```

核对两份配置的镜像名与本机标签一致；第 1 节使用了自定义镜像时，同步修改模拟配置的 `images`。以下无网络加载检查使用默认 AISBench 标签，自定义时也须替换该标签：

```bash
llm-bench images check --config "$CPU_CONFIG"
docker run --rm --pull=never --platform linux/amd64 --network none \
  --mount "type=bind,src=$CPU_TOKENIZER_DIR,dst=/tokenizer,readonly" \
  -e OPENBLAS_NUM_THREADS=1 -e OMP_NUM_THREADS=1 \
  -e MKL_NUM_THREADS=1 -e NUMEXPR_NUM_THREADS=1 \
  -e TOKENIZERS_PARALLELISM=false \
  --entrypoint python llm-benchmark-aisbench:e330dc1-amd64 \
  -c 'from transformers import AutoTokenizer; t=AutoTokenizer.from_pretrained("/tokenizer", local_files_only=True, trust_remote_code=False); print(type(t).__name__, t.encode("tokenizer CPU check"))'
```

应成功输出 tokenizer 类型和编码结果。缺文件、外部软链接或自定义代码依赖导致失败时，先整理完整目录再继续；不要改回模拟词表来替代这项检查。旧运行时若报线程创建失败，按[线程兼容指南](旧版容器运行时线程兼容指南.md)核查；同一模拟模板默认的兼容设置不影响上述手工 docker 命令。

**执行模拟压测和验收。** 本次 up 会执行 8 次正式请求、并发 2；此处不加 `--no-benchmark`。

```bash
llm-bench plan --config "$CPU_CONFIG"
llm-bench up --config "$CPU_CONFIG"
python scripts/verify_simulation.py --config "$CPU_CONFIG"
```

成功标准：AISBench 正式请求成功 8、失败 0；验证器检查容器状态、Prometheus targets、模拟 GPU 指标、Grafana 数据源/面板、Loki 请求日志和最新一次默认 up 的报告。证据写入 `generated/online-cpu-smoke/verification.json`，该次原始 AISBench 报告位于其 `data/results/<时间目录>/` 下。

Grafana 为 `http://<在线机IP>:33005`，Prometheus 为 `http://<在线机IP>:39095`。模拟服务只暴露部分演示指标，其余真实 vLLM/SGLang 面板出现 No data 属正常。初始 Grafana 账号按镜像默认 `admin/admin`；使用了已有持久目录并修改过密码时，运行验证器前设置 `BENCH_GRAFANA_PASSWORD`。验证器读取默认 up 的报告，不用它判断后续 bench run 是否通过。

通过后，可在同一模拟栈追加小规模测试，完成后关闭：

```bash
llm-bench bench run --config "$CPU_CONFIG" \
  --input-len 128 --output-len 64 --concurrency 2 --requests 20
llm-bench logs check --config "$CPU_CONFIG"
llm-bench down --config "$CPU_CONFIG"
```

追加测试以本次 `data/results/suites/<运行目录>/suite-results.json` 的 `passed: true`、实际请求数和零失败为准。down 保留 tokenizer、日志和结果；再次 up 或修改配置前，先停止原模拟栈。若失败，先用 `llm-bench logs collect --config "$CPU_CONFIG"` 收集证据，再 down。

若要将下载的 tokenizer 随包交付，在回到第 1 节打包时传入该目录：

```bash
TOKENIZER_DIR="$CPU_TOKENIZER_DIR" REF=main OFFLINE_PYTHON=3.11 \
  bash scripts/build_offline_bundle.sh
```

打包脚本会携带该目录中筛选后的 tokenizer 文件，并在自动冒烟中使用它。已生成的旧压缩包不会随目录变化而更新；真实服务压测须使用与实际模型匹配的 tokenizer，不能将此处 Qwen3 示例用于其他模型。

## 2. 离线机导入并一键部署（不发起压测）

提前安装 Docker 或 nerdctl/containerd、相应 GPU/DCU 驱动和容器运行时，以及与 `OFFLINE_PYTHON` 相同版本的 CPython（含 venv/pip）。这些主机软件与模型权重不在包内。当前用户须有容器运行权限及配置中目录的读写权限。启动推理服务，确认 `/v1/models`、`/metrics` 和真实日志可访问。

将压缩包和校验文件复制到离线机同一目录：

```bash
sha256sum -c llm-bench-offline-*.tar.gz.sha256
tar -xzf llm-bench-offline-<提交>-<时间>.tar.gz
cd llm-bench-offline-<提交>-<时间>
vi site.yaml
```

按 `site.yaml` 中的 **【必改】** 注释核对：此机真实 IP/推理端口、模型 ID、tokenizer/日志/结果目录、日志文件、GPU 厂商/数量/节点名、TP/PP 和正式 workload。推理服务须监听容器可访问的本机 IP 或 `0.0.0.0`；桥接容器中的 `127.0.0.1` 指向容器自身。若使用包内 tokenizer，可将 `storage.tokenizer` 改为解压后 `tokenizer/` 的**绝对路径**。`storage.logs` 下配置的日志文件必须真实存在，勿创建空文件替代真实服务日志。

Docker 默认使用 `runtime: [docker]`。nerdctl 改为 `runtime: [nerdctl, --namespace, benchmark]`，导入及启动自动复用该 namespace。保持 `offline: true`、`simulation: false`。有鉴权时取消 `api_key_env` 注释，在本机 shell 设置对应环境变量；若指标不鉴权，可设置 `topology.metrics_api_key_env: null`。

```bash
# 有鉴权时设置（只输入 Token 本身，不带 Bearer 前缀）
# read -rsp 'Inference token: ' INFERENCE_API_KEY; export INFERENCE_API_KEY; echo
PYTHON=python3.11 bash repo/scripts/deploy_offline.sh
source ./env.sh
SITE="$PWD/site.yaml"
llm-bench status --config "$SITE"
```

脚本校验包内不可变文件，使用 `pip --no-index` 安装包内 wheel，导入镜像，检查镜像并执行 `llm-bench up --no-benchmark`。部署会检查服务/指标就绪，**不会发送 AISBench 冒烟或压测 workload**。推理服务由原有部署管理，不由本脚本启动。`site.yaml` 可现场编辑，不在包内逐文件校验清单中；源码、镜像、wheel 和验证元数据均在清单中。

## 3. 用 llm-bench 逐级测试

从上述 bundle 根目录执行；新 shell 先重新 `source ./env.sh` 并设置 `SITE` 和所需鉴权环境变量。每步成功后再继续下一步：

```bash
# 冒烟：1 并发、4 请求，先确认真实模型、鉴权、tokenizer 和流式接口可用
llm-bench bench run --config "$SITE" \
  --input-len 32 --output-len 16 --concurrency 1 --requests 4

# 小规模：2 并发、20 请求；检查响应成功、延迟、GPU/CPU/日志
llm-bench bench run --config "$SITE" \
  --input-len 128 --output-len 64 --concurrency 2 --requests 20

# 正式压测：使用已审核的 site.yaml 中 benchmark 参数（示例 1k/1k、16 并发、1000 请求）
llm-bench bench run --config "$SITE"

# 查看日志采集状态；测试结束后关闭观测栈，保留数据
llm-bench logs check --config "$SITE"
llm-bench down --config "$SITE"
```

`bench run` 只对当前运行栈的 workload 做参数覆盖。若修改 `site.yaml` 的模型、路径、GPU、端口或正式参数，先 `down` 再重新部署；运行中的栈使用启动时保存的配置。测试按顺序执行，勿同时运行不同 workload。默认结果在 `storage.root/data/results/suites/<时间>/`，`suite-results.json` 中每例应为 `passed: true`、`status: complete`，AISBench 汇总的 Failed Requests 应为 0。Grafana 默认 `http://<此机IP>:33000`，初始账号按镜像默认 `admin/admin`，首次登录后修改密码，密码变更保存在持久数据目录。

同机压测会与推理服务共享 CPU、内存和网络资源，正式并发应根据小规模测试逐步提高，同时观察客户端是否成为瓶颈。Grafana 任务总览的 node-exporter 主机资源区域可查看 CPU/I/O 等待、负载、内存、文件系统、磁盘和网络；通过“主机采集目标”筛选，单机模板保持 `host_metrics: host` 才能完整采集宿主机。详细口径见[任务观测说明](任务指标与日志观测指南.md#主机资源的筛选与采集口径)。失败时停止后续档位，用 `llm-bench logs collect --config "$SITE"` 收集诊断包；部署失败也保留栈和日志，先定位再用 `down` 清理后重试。不要直接反复执行部署脚本覆盖活跃栈。

## YAML 迁移说明

`configs/` 中部署、交付、suite、search、环境、GPU/网络适配和 Dashboard 源配置均改为 `.yaml`；源码运行前先 `python3 -m pip install -r requirements.txt`。旧的外部 JSON 配置仍可读取，推荐改用 YAML；`create_site_config.py` 默认输出 `generated/site/site.yaml`。模板中的字符串若类似布尔值（如 `"off"`）或数字，请加引号；重复键会报错。

tokenizer 的 `tokenizer*.json`、ShareGPT/JSONL 数据集、运行状态/测试报告和 `references/` 中的上游原始资料保留原格式。Grafana 运行时仍需 JSON Dashboard，由 YAML 源自动渲染；Prometheus/Grafana provisioning 现在生成常规 YAML。无需手工修改 `storage.root/config/<哈希>/` 中的渲染文件。
