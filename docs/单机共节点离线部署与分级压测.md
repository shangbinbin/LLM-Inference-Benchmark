# 单机共节点：在线打包、离线部署与分级压测

适用于 Linux x86_64，推理服务与压测/观测链路在同一台 GPU/DCU 节点。推理服务、模型权重、设备驱动和 GPU 容器运行时须提前部署；本工具部署 Prometheus、Grafana、Loki、Alloy、Exporter、日志轮转及 AISBench 客户端。在线机无需 GPU，其模拟冒烟验证软件链路；离线机可先用包内 tokenizer 重复模拟测试，再验证真实服务。

## 1. 在线机一键构建交付包

准备 Git、可访问的 Docker daemon、Python 3.9+（含 venv/pip）、GNU tar/coreutils，以及足够的构建/镜像导出磁盘空间（建议至少 30 GB）。网络须可访问选用的工程源码仓库（国内使用 Gitee）、ModelScope 模型文件服务、镜像源、PyPI，以及 AISBench 上游源码的 GitHub/codeload.github.com 和构建所用的 Debian/PyTorch 等依赖源；私有镜像先完成 `docker login`。

本工程的 Gitee 地址为 `git@gitee.com:Ayanami_Rei_0/LLM-Inference-Benchmark.git`，与 GitHub 仓库 `https://github.com/shangbinbin/LLM-Inference-Benchmark.git` 同步，按同一套提交版本管理。国内操作统一使用 Gitee；SSH 地址需要在线机当前用户已配置可访问该仓库的 SSH 密钥。

首次操作可在自选的可写目录取得启动脚本，无需提前准备专门的构建源码目录：

```bash
git clone git@gitee.com:Ayanami_Rei_0/LLM-Inference-Benchmark.git
cd LLM-Inference-Benchmark
```

已有本地仓库时进入原仓库目录并更新启动脚本；`origin` 指向 Gitee 时仍使用 `git pull --ff-only origin main`。下面命令均在仓库根目录运行。脚本会另建目录重新拉取远端，**只打包远端已提交的版本**：

```bash
REPO_URL=git@gitee.com:Ayanami_Rei_0/LLM-Inference-Benchmark.git \
REF=main OFFLINE_PYTHON=3.9 \
  bash scripts/build_offline_bundle.sh
```

默认会自动下载 Qwen3-0.6B tokenizer，完成无 GPU 全链路模拟测试，再生成包含该 tokenizer 的交付包。无需先手工下载。

**Python 版本分层：** 在线/离线宿主机支持 Python 3.9+，离线交付默认针对 3.9；AISBench/toolbox 镜像内部继续使用 Python 3.11，宿主机无需与容器版本一致。在线下载依赖固定为支持 Python 3.9 的 `modelscope==1.33.0`，只安装到构建工作目录的虚拟环境，离线机使用包内 `pip==25.3` wheel 引导虚拟环境，再安装 `requirements.txt` 中的 PyYAML，无需系统预装 ensurepip/pip。例如离线机为 Python 3.10.12，打包时写 `OFFLINE_PYTHON=3.10`，部署时写 `PYTHON=/usr/bin/python3`。若离线机实际使用 3.11，打包时设 `OFFLINE_PYTHON=3.11`，导入时设 `PYTHON=python3.11`；旧包仍按各自 `metadata/offline-python.txt` 记录的版本部署。

两个在线打包脚本的 `REPO_URL` 默认值仍为 GitHub，**不会根据本地仓库的 origin 自动选择源**。因此，即使本地代码通过 Gitee 拉取，打包时也要像示例一样显式指定 Gitee。`REPO_URL` 只切换本工程源码来源；AISBench 上游源码、镜像、pip 和 ModelScope 下载地址分别由各自流程决定。自建镜像仓库或不同交付选择可先修改一份 YAML，然后指定绝对路径：

```bash
REPO_URL=git@gitee.com:Ayanami_Rei_0/LLM-Inference-Benchmark.git \
REF=main OFFLINE_PYTHON=3.9 \
SITE_CONFIG=/opt/build/site.yaml \
DELIVERY_CONFIG=/opt/build/offline-images.yaml \
TOKENIZER_DIR=/opt/models/Qwen3-0.6B \
OUTPUT_DIR=/opt/delivery \
  bash scripts/build_offline_bundle.sh
```

上述参数都是脚本的环境变量，省略或置空时采用下表默认值；shell 中已 `export` 的同名变量也会生效。`SITE_CONFIG`、`DELIVERY_CONFIG`、`TOKENIZER_DIR` 指定时必须为在线机已有文件/目录的绝对路径。

| 参数 | 作用 | 省略时的默认值及行为 |
| --- | --- | --- |
| `REPO_URL` | 拉取源码的 Git 仓库地址，可改为有访问权限的镜像或内部仓库 | `https://github.com/shangbinbin/LLM-Inference-Benchmark.git`；国内显式设为 `git@gitee.com:Ayanami_Rei_0/LLM-Inference-Benchmark.git`。始终重新 clone，不读取本地 origin，也不直接打包当前工作区 |
| `REF` | 构建的远端分支、标签或提交号 | `main`；使用拉取时远端 main 的提交。本地未推送的修改不会进入包内；复现交付时填写固定提交号 |
| `OFFLINE_PYTHON` | 离线机 CPython 主次版本，用于下载匹配的 Linux x86_64 wheel 并在导入时校验 | `3.9`；支持 3.9 及以上的 CPython 主次版本，如 `3.11`。不是在线机 Python 的切换开关，也不会安装离线机 Python。离线机须提前安装匹配版本及标准库 venv 模块；包内 pip wheel 可替代系统 ensurepip，其他版本还须有对应依赖 wheel |
| `SITE_CONFIG` | 打包进 `site.yaml` 的现场模板；构建/冒烟从中读取镜像名，生产地址、GPU、日志等在离线机核对 | 拉取版本中的 `configs/sites/single-node.example.yaml`；它含示例 IP 和路径，不能原样用于真实部署。自动冒烟始终使用 fixture，不会访问其中的真实推理地址 |
| `DELIVERY_CONFIG` | 选择交付的设备 Exporter 和额外镜像，生成 `delivery.yaml` | 拉取版本中的 `configs/delivery/offline-images.yaml`；默认导出公共镜像及 NVIDIA、海光两种 Exporter。海光私有源不可访问时，传入仅选择所需厂商的配置；仅交付 CPU 模拟可将 `selected_gpu_exporters` 设为 `[]` |
| `TOKENIZER_DIR` | 复用在线机已有 tokenizer，替代默认下载；复制 tokenizer、词表、配置和模板，不复制模型权重 | 不设置时通过 ModelScope 自动下载 `Qwen/Qwen3-0.6B` 的 tokenizer 相关文件。设置时跳过下载，须包含有效的 `tokenizer_config.json` 和 `tokenizer.json`，并能被镜像中的 Transformers 本地加载；测试与打包均使用这份文件，不回退到 mock tokenizer |
| `TOKENIZER_REVISION` | 默认下载的 ModelScope 模型版本，可设提交号或标签 | `master`；会随上游更新。需要复现时指定固定版本。设置 `TOKENIZER_DIR` 时不参与下载，本地文件来源及文件哈希另行记录 |
| `OUTPUT_DIR` | 成功压缩包、校验文件以及保留的构建工作目录位置 | **执行脚本时当前目录**下的 `generated/delivery/`；可指定 `/opt/delivery` 等可写目录，不是离线机的部署目录 |
| `SMOKE_PORT_BASE` | 在线自动模拟测试的七个宿主机端口起点 | `43000`；按模板顺序使用 `43000..43006`（Grafana、Prometheus、Loki、Alloy、node-exporter、预留 gpu-exporter、fixture）。必须空闲；合法范围 `1024..65529`。只影响本次模拟测试，不改变现场 `site.yaml` 的端口 |

两个示例执行同一流程，均显式使用 Gitee。第一条的其余配置使用默认值并自动下载 tokenizer；第二条使用自定义现场/镜像交付配置、已有 tokenizer 和输出目录。若只想复用已下载的 Qwen3 tokenizer，在国内源码设置之外增加 `TOKENIZER_DIR` 即可，无需另备现场或镜像交付 YAML：

```bash
REPO_URL=git@gitee.com:Ayanami_Rei_0/LLM-Inference-Benchmark.git \
TOKENIZER_DIR=/opt/models/Qwen3-0.6B \
REF=main OFFLINE_PYTHON=3.9 \
  bash scripts/build_offline_bundle.sh
```

### 1.1 自动下载、无 GPU 测试与交付内容

脚本依次执行：

1. 拉取远端代码并记录提交，安装在线工具依赖，准备目标 Python 的 PyYAML wheel 和通用 pip 25.3 引导 wheel。
2. 自动下载 Qwen3-0.6B tokenizer（或复用 `TOKENIZER_DIR`），筛选文件并记录来源、版本参数和逐文件 SHA-256。ModelScope SDK 仅在在线下载时安装，不需要在离线机安装。
3. 运行单元测试，构建 toolbox/AISBench，拉取并检查所选交付镜像的 Linux amd64 架构。
4. 生成独立 CPU 模拟配置，使用**待交付的 tokenizer 文件**，以 `dataset_type: tokenid` 生成 64-token 输入，向 fixture 发起 8 次正式请求、并发 2、请求输出 16 token。镜像采用本地模式，客户端设置离线加载，不依赖 GPU、驱动、模型权重或真实推理服务。
5. 通过 `llm-bench verify` 验收容器、AISBench 零失败报告、Prometheus targets、模拟 GPU 和 node-exporter 指标、Grafana 面板/数据源、Loki 请求日志；关闭模拟栈。
6. **全部通过后**导出本地镜像、计算校验和并生成交付压缩包。模拟失败不进入镜像导出和成功包发布步骤。

fixture 的响应和设备指标是模拟数据；真实 tokenizer 用于验证客户端输入生成与结果处理。此测试覆盖软件链路，不能作为 Qwen3 的真实推理性能或 GPU 容量结论，部分真实 vLLM/SGLang 专属面板显示 No data 属正常。

输出为 `OUTPUT_DIR/llm-bench-offline-<提交>-<UTC时间>.tar.gz` 及 `.sha256`。包内包含：

| 路径 | 内容 |
| --- | --- |
| `repo/`、`images/`、`wheelhouse/` | 已记录提交的源码、交付镜像归档和离线 Python 依赖（含 pip 引导 wheel） |
| `tokenizer/` | 默认下载的 Qwen3-0.6B tokenizer；指定本地目录时为筛选后的本地 tokenizer。不含模型权重、下载 SDK 或下载缓存 |
| `site.yaml`、`delivery.yaml` | 可现场编辑的真实服务配置模板和镜像交付选择 |
| `metadata/tokenizer.json` | tokenizer 来源、下载版本参数及文件 SHA-256；`master` 是请求版本，文件哈希用于确认本次实际交付内容 |
| `metadata/online-smoke.json`、`metadata/online-smoke.yaml` | 在线全链路验收结果及配置快照；快照含在线机构建路径，仅用于追溯，离线机不能直接使用 |
| `metadata/unit-tests.log`、`metadata/revision.txt` | 单元测试记录及源码提交 |
| `SHA256SUMS`、`操作说明.md` | 包内不可变文件校验清单及本文 |

任一步失败均返回非零，保留 `OUTPUT_DIR/.build-*/build.log`、下载缓存和已有诊断数据，不产出本次成功压缩包。网络无法下载 tokenizer 时先修复网络，或使用已验证的本地 `TOKENIZER_DIR` 重试；不会静默改用模拟词表。不要从构建中的 `.build-*` 目录提前拷包。下载/构建涉及的 pip 镜像和代理可按在线机环境配置；有代理时容器间 fixture、Prometheus、Loki 等服务名应绕过外部代理。

下载日志中的 `Download model ... successfully` 表示 tokenizer 已下载；`Target directory already exists, skipping creation` 是 SDK 提示，不代表后续全流程通过。下载后会生成模拟配置并运行单元测试，然后才开始镜像构建。新版脚本输出 `[build] <阶段>`，测试失败会把日志最后 100 行同步打印到终端。旧版本若只显示 `Build failed`，进入提示中的 `.build-*` 目录查看：

```bash
# 在本次失败的 .build-* 目录执行，保留构建目录以便诊断。
tail -n 100 llm-bench-offline-*/metadata/unit-tests.log
tail -n 100 build.log
git --version
bash --version
```

测试阶段也需兼容构建机的 Git：新版测试已使用兼容旧 Git 的建库方式；旧版本若在日志中报 `git init -b` 的 unknown option，先更新本地仓库并重新执行，不需要为此跳过测试或升级系统 Git。其他失败按具体日志处理，不能仅凭 SDK 提示判断原因。

旧版 Bash 执行早期脚本时，默认下载路径可能报 `tokenizer_args[@]: unbound variable`：这是 `set -u` 与空数组展开的兼容问题，和 pip 升级提示无关。先通过 `git pull --ff-only origin main` 更新本地启动脚本（独立下载脚本的用户重新下载最新版），再重新执行打包命令。仅设置 `REF=main` 不会更新已经启动的外层脚本；修复后无需通过指定本地 tokenizer 绕过自动下载，也无需升级系统 Bash。

## 2. 离线机导入并一键部署（不发起压测）

### 2.1 先导入并用包内 tokenizer 做无 GPU 全链路模拟

离线 Linux x86_64 机器只需 Docker 或 nerdctl/containerd，以及与 `OFFLINE_PYTHON` 一致的 CPython（含标准库 venv 模块；ensurepip/pip 可缺省）。此分支无需 GPU、驱动、真实服务、外部模型目录或互联网；导入过程不会启动容器、冒烟或压测。

将本次压缩包及 `.sha256` 复制到离线机同一目录，替换下面文件名中的占位符：

```bash
sha256sum -c llm-bench-offline-<提交>-<时间>.tar.gz.sha256
tar -xzf llm-bench-offline-<提交>-<时间>.tar.gz
cd llm-bench-offline-<提交>-<时间>
# 默认 Docker；nerdctl 先将 site.yaml 中 runtime 改为 [nerdctl, --namespace, benchmark]
PYTHON=python3.9 bash repo/scripts/deploy_offline.sh --simulation
source ./env.sh
SIM="$PWD/offline-simulation.yaml"
```

该模式仅从 `site.yaml` 读取 `images` 和 `runtime`，不校验真实服务的示例 IP、日志或模型路径。脚本校验包括 tokenizer 和 pip wheel 在内的包内文件，用 `venv --without-pip` 创建虚拟环境，需要时直接从包内 pip wheel 离线引导，再通过 `pip --no-index` 安装项目 wheel，向所选 runtime/namespace 导入镜像，并生成 `offline-simulation.yaml`。其 tokenizer 自动指向**当前解压目录**的 `tokenizer/` 绝对路径，数据和日志保存在 `generated/offline-smoke/`、`generated/offline-smoke-logs/`；保持 `simulation: true`、`host_metrics: container`、`offline: true` 和 `dataset_type: tokenid`。

离线模拟端口默认使用 `44000..44006`；导入时可设置 `SMOKE_PORT_BASE=45000` 换用另一组空闲端口。需要调整 runtime、端口或路径时先关闭原模拟栈，再修改配置/重新导入；脚本拒绝覆盖活跃模拟栈。

导入完成后，使用 llm-bench 明确启动并验收：

```bash
llm-bench plan --config "$SIM"
llm-bench up --config "$SIM"
llm-bench verify --config "$SIM"
# 通过后可继续做小规模模拟测试
llm-bench bench run --config "$SIM" \
  --input-len 128 --output-len 64 --concurrency 2 --requests 20
llm-bench logs check --config "$SIM"
llm-bench down --config "$SIM"
```

`up` 会运行默认 8 请求、并发 2 的 tokenid 冒烟；`verify` 不发起新 workload，检查本次默认 up 的报告和完整观测链路。验收结果在 `generated/offline-smoke/verification.json`，默认 AISBench 报告在该目录的 `data/results/<时间>/` 下。追加 `bench run` 的结果另存于 `data/results/suites/<运行目录>/suite-results.json`，应为 `passed: true`、`status: complete` 且请求零失败；不要用 verify 验收追加 suite。

Grafana 默认 `http://<离线机IP>:44000`，Prometheus 为 `http://<离线机IP>:44001`。初始 Grafana 账号按镜像默认 `admin/admin`；复用数据目录且修改过密码时，运行 verify 前设置 `BENCH_GRAFANA_PASSWORD`。down 保留 tokenizer 和结果，再次测试可直接 up，无需重新导入。移动整个解压目录前先 down，移动后重新导入生成新路径。失败时先执行 `llm-bench logs collect --config "$SIM"` 收集诊断，再 down。

若旧包在创建虚拟环境时报 `ensurepip is not available` / 提示安装 `python3.10-venv`，这是系统拆分了 Python 引导组件。新版完整包在 `wheelhouse/` 携带 pip 25.3，可在无需联网、无需系统 ensurepip 的情况下部署。请在线更新仓库后，按离线机版本重新构建，例如 `OFFLINE_PYTHON=3.10`，再将新包解压到新目录运行部署脚本。也可为旧包离线安装与目标发行版、Python 包版本匹配的系统 venv 包及其依赖后重试；不要在离线机直接执行需要联网的 apt 命令。

旧包若没有 pip wheel，更新脚本会给出明确补齐提示；只替换启动脚本或只交付代码更新包不能补上缺失的依赖物料。若 Python 连 `venv --without-pip` 都不可用，仍需先补齐标准库 venv 模块。引导仅写入交付目录的 `.venv/`，不改变系统 Python；导入阶段依然不启动冒烟测试。

### 2.2 部署真实单机共节点服务的观测链路

完成模拟测试并 down 后，按本节填写真实配置。使用默认模式的一键部署同样会生成 `offline-simulation.yaml`，随后也可按 2.1 节单独模拟；模拟与真实配置的项目名、数据目录及默认端口独立。

提前安装 Docker 或 nerdctl/containerd、相应 GPU/DCU 驱动和容器运行时，以及与 `OFFLINE_PYTHON` 相同版本的 CPython（含标准库 venv 模块；无需系统 ensurepip/pip）。这些主机软件与模型权重不在包内。当前用户须有容器运行权限及配置中目录的读写权限。启动推理服务，确认 `/v1/models`、`/metrics` 和真实日志可访问。

将压缩包和校验文件复制到离线机同一目录：

```bash
sha256sum -c llm-bench-offline-*.tar.gz.sha256
tar -xzf llm-bench-offline-<提交>-<时间>.tar.gz
cd llm-bench-offline-<提交>-<时间>
vi site.yaml
```

按 `site.yaml` 中的 **【必改】** 注释核对：此机真实 IP/推理端口、模型 ID、tokenizer/日志/结果目录、日志文件、GPU 厂商/数量/节点名、TP/PP 和正式 workload。推理服务须监听容器可访问的本机 IP 或 `0.0.0.0`；桥接容器中的 `127.0.0.1` 指向容器自身。默认包内为 Qwen3-0.6B tokenizer，真实模型必须与其匹配；其他模型须准备对应 tokenizer。若使用包内 tokenizer，可将 `storage.tokenizer` 改为解压后 `tokenizer/` 的**绝对路径**。`storage.logs` 下配置的日志文件必须真实存在，勿创建空文件替代真实服务日志。

Docker 默认使用 `runtime: [docker]`。nerdctl 改为 `runtime: [nerdctl, --namespace, benchmark]`，导入及启动自动复用该 namespace。保持 `offline: true`、`simulation: false`。有鉴权时取消 `api_key_env` 注释，在本机 shell 设置对应环境变量；若指标不鉴权，可设置 `topology.metrics_api_key_env: null`。

```bash
# 有鉴权时设置（只输入 Token 本身，不带 Bearer 前缀）
# read -rsp 'Inference token: ' INFERENCE_API_KEY; export INFERENCE_API_KEY; echo
PYTHON=python3.9 bash repo/scripts/deploy_offline.sh
source ./env.sh
SITE="$PWD/site.yaml"
llm-bench status --config "$SITE"
```

脚本校验包内不可变文件，使用 `pip --no-index` 安装包内 wheel，导入镜像，检查镜像并执行 `llm-bench up --no-benchmark`。部署会检查服务/指标就绪，**不会发送 AISBench 冒烟或压测 workload**。推理服务由原有部署管理，不由本脚本启动。`site.yaml` 可现场编辑，不在包内逐文件校验清单中；源码、镜像、wheel、tokenizer 和验证元数据均在清单中。

## 3. 用 llm-bench 逐级测试

从上述 bundle 根目录执行；新 shell 先重新 `source ./env.sh` 并设置 `SITE` 和所需鉴权环境变量。每步成功后再继续下一步：

```bash
# 冒烟：1 并发、4 请求，先确认真实模型、鉴权、tokenizer 和流式接口可用
llm-bench bench run --config "$SITE" \
  --input-len 32 --output-len 16 --concurrency 1 --requests 4

# 小规模：2 并发、20 请求；检查响应成功、延迟、GPU/CPU/日志
llm-bench bench run --config "$SITE" \
  --input-len 128 --output-len 64 --concurrency 2 --requests 20

# 正式压测：使用已审核的 site.yaml 中 benchmark 参数（示例 1k/1k、16 并发、1000 请求）
llm-bench bench run --config "$SITE"

# 查看日志采集状态；测试结束后关闭观测栈，保留数据
llm-bench logs check --config "$SITE"
llm-bench down --config "$SITE"
```

`bench run` 只对当前运行栈的 workload 做参数覆盖。若修改 `site.yaml` 的模型、路径、GPU、端口或正式参数，先 `down` 再重新部署；运行中的栈使用启动时保存的配置。测试按顺序执行，勿同时运行不同 workload。默认结果在 `storage.root/data/results/suites/<时间>/`，`suite-results.json` 中每例应为 `passed: true`、`status: complete`，AISBench 汇总的 Failed Requests 应为 0。Grafana 默认 `http://<此机IP>:33000`，初始账号按镜像默认 `admin/admin`，首次登录后修改密码，密码变更保存在持久数据目录。

同机压测会与推理服务共享 CPU、内存和网络资源，正式并发应根据小规模测试逐步提高，同时观察客户端是否成为瓶颈。Grafana 任务总览的 node-exporter 主机资源区域可查看 CPU/I/O 等待、负载、内存、文件系统、磁盘和网络；通过“主机采集目标”筛选，单机模板保持 `host_metrics: host` 才能完整采集宿主机。详细口径见[任务观测说明](任务指标与日志观测指南.md#主机资源的筛选与采集口径)。失败时停止后续档位，用 `llm-bench logs collect --config "$SITE"` 收集诊断包；部署失败也保留栈和日志，先定位再用 `down` 清理后重试。不要直接反复执行部署脚本覆盖活跃栈。

## 4. 仅更新代码，复用已有离线环境

后续只更新 CLI、压测调度、Dashboard/采集配置或文档时，可以交付代码更新包，合入之前完整交付包解压得到的目录。目标目录须已有 `repo/`、`metadata/revision.txt`、`SHA256SUMS` 和安装好的 `.venv/`。该入口使用完整的受管源码快照和明确的基线提交，无需离线 Git 仓库，也不执行 `git pull`。

代码包包含 `repo/`、`metadata/code-update.json`、`metadata/unit-tests.log` 和 `SHA256SUMS`，体积不包含镜像、wheel、tokenizer 或虚拟环境。在线仅拉取代码、检查兼容性、运行单元测试并打包，无需 Docker/GPU；离线仅应用代码，不安装依赖、不导入/构建/拉取镜像、不启动容器或测试。

**适用边界：** 新旧版本的 `containers/`、`.dockerignore`、`requirements.txt`、`requirements-build.txt`、`requirements-bootstrap.txt`、`Stack.build_one` 构建逻辑和 `configs/sites/`、`configs/stacks/` 中的镜像引用集合必须保持一致。涉及这些内容的变更会被拒绝，改走第 1 节完整交付流程。容器目录中的脚本变更也按此保守规则处理。兼容性检查不替代离线运行验收；代码包的在线单元测试不包含容器全链路冒烟。

### 4.1 确认离线基线并停止原有栈

在**已有完整交付包根目录**记录当前源码版本；每次代码更新后这里都会记录新版本：

```bash
cd /opt/llm-bench/current
cat metadata/revision.txt
source ./env.sh
# 用更新前的 CLI 关闭本次环境管理的所有栈，保留监控数据、日志和结果。
# 只执行实际存在的栈对应命令；自定义配置也须逐个停止。
llm-bench down --config "$PWD/site.yaml"
# 若模拟栈也在运行：
# llm-bench down --config "$PWD/offline-simulation.yaml"
```

`/opt/llm-bench/current` 是示例路径，替换为实际完整交付目录；BASE_REF 使用上面输出的 **40 位提交号**，不要填“上次打包时 main 这个分支名”。停止的是压测观测栈，推理服务仍由现场原有方式管理。需要诊断时先收集日志再 down；不要删 `state.json` 或锁文件绕过检查。

### 4.2 在线机仅构建代码更新包

在已更新的仓库根目录执行：

```bash
REPO_URL=git@gitee.com:Ayanami_Rei_0/LLM-Inference-Benchmark.git \
BASE_REF='<离线机 metadata/revision.txt 的完整提交号>' \
REF=main \
  bash scripts/build_code_update.sh
```

| 参数 | 作用与默认行为 |
| --- | --- |
| `BASE_REF` | **必填，无默认值**。离线机当前部署代码的提交号；在线可解析 Git 引用，但解析后的提交必须与离线记录完全一致。多次更新须以最近一次成功更新后的提交为基线 |
| `REF` | 新代码的分支、标签或提交，默认 `main`；只包含远端已提交、已推送的内容。与基线相同会拒绝生成无变化包 |
| `REPO_URL` | 默认 `https://github.com/shangbinbin/LLM-Inference-Benchmark.git`；国内像示例一样显式指定 `git@gitee.com:Ayanami_Rei_0/LLM-Inference-Benchmark.git`，不会读取本地 origin。也支持有访问权限的内部镜像仓库 |
| `OUTPUT_DIR` | 默认在线机执行目录下的 `generated/code-delivery/`；可设为 `/opt/delivery/code` 等可写目录 |

代码包沿用已有环境的 Python、依赖、镜像和 tokenizer，不需要设置完整交付的 `OFFLINE_PYTHON`、`TOKENIZER_DIR` 等参数。

在线机需要 Git、Python 3.9+（含 venv/pip）、tar/coreutils，以及访问源码仓库和 PyPI 的能力。脚本在独立工作目录重新 clone，在线依赖只安装到工作目录 venv，不改变系统 Python。输出为 `llm-bench-code-<基线12位>-to-<新版本12位>-<UTC时间>.tar.gz` 及 `.sha256`；测试或兼容检查失败时保留 `.build-*/build.log`、`unit-tests.log`，不产出本次成功代码包。

### 4.3 离线解压并合入已有目录

把代码压缩包及其 `.sha256` 传到离线机的独立接收目录，替换文件名后执行；**不要直接解压覆盖已有 repo**：

```bash
cd /opt/delivery/code
sha256sum -c 'llm-bench-code-<基线>-to-<新版本>-<时间>.tar.gz.sha256'
tar -xzf 'llm-bench-code-<基线>-to-<新版本>-<时间>.tar.gz'
cd 'llm-bench-code-<基线>-to-<新版本>-<时间>'
bash repo/scripts/apply_code_update.sh /opt/llm-bench/current
# 使用自定义外部配置时，显式列出其存储位置以检查活跃栈；可重复 --config。
# bash repo/scripts/apply_code_update.sh /opt/llm-bench/current \
#   --config /etc/llm-bench/production.yaml
```

目标参数是**完整交付根目录**，不带 `/repo`；脚本默认使用目标 `.venv/bin/python`，也可用 `PYTHON=/path/to/python` 指定已安装 PyYAML 的 Python 3.9+。更新包必须解压在目标目录之外，执行入口来自新解压的代码包。

应用前检查：代码包校验和、基线提交、原有受管源码及执行权限、新文件与自定义文件冲突、已知栈的状态与运行锁。默认检查 `site.yaml`、`offline-simulation.yaml`、CLI 保存的运行引用和常见 generated 状态目录；使用其他外部配置/数据目录时必须逐个传入 `--config`。受管源码有本地修改时会列出冲突并拒绝合入；先备份、将现场配置迁出源码模板，再处理冲突，不提供强制覆盖选项。

成功后替换变化文件、删除新版本已移除的受管文件，清理相关 Python 字节码缓存以保证新代码生效，保留其他未受管文件以及根目录的现场 `site.yaml`、`delivery.yaml`、`offline-simulation.yaml`、`env.sh`、`.venv/`、`images/`、`wheelhouse/`、`tokenizer/`、generated 数据和结果。`repo/configs/` 中的受管模板会随源码更新，现场参数应放在根目录 site.yaml 或独立自定义文件中。

版本追溯：`metadata/revision.txt` 更新为当前代码提交；`metadata/image-revision.txt` 保留原始镜像交付时的提交；`metadata/code-update.json` 记录本次起止版本和备份 ID。校验清单更新为新源码和更新记录的哈希，沿用原有镜像、tokenizer、wheel 等物料的校验记录，不重新扫描大镜像文件。原始在线容器冒烟证据保留；本次单元测试日志为 `metadata/code-update-tests.log`。

### 4.4 更新后重新启动与验收

回到已有交付目录，重新加载环境。选择模拟或真实服务其中一条路线，不需要再执行会重新导入镜像的 deploy 脚本：

```bash
cd /opt/llm-bench/current
source ./env.sh
cat metadata/revision.txt
# 包内 tokenizer 的无 GPU 全链路复测：
SIM="$PWD/offline-simulation.yaml"
llm-bench images check --config "$SIM"
llm-bench up --config "$SIM"
llm-bench verify --config "$SIM"
llm-bench down --config "$SIM"
# 真实服务路线则执行以下命令，并按第 3 节继续分级测试：
# SITE="$PWD/site.yaml"
# llm-bench images check --config "$SITE"
# llm-bench up --config "$SITE" --no-benchmark
# llm-bench bench run --config "$SITE" --input-len 32 --output-len 16 --concurrency 1 --requests 4
```

更新中的模板、面板和采集代码在重新 up 时生效；现场配置保持 `offline: true`。如果目标还没有 `offline-simulation.yaml`，按第 2.1 节先生成模拟配置。若新版本调整了现场配置字段，结合 `repo/` 中新文档手工迁移已有 site.yaml 后再启动；代码更新不会自动覆盖现场配置。

### 4.5 回滚或恢复中断更新

更新备份保存在目标 `.code-updates/<备份ID>/`，仅备份受影响的代码文件、版本和校验记录。普通执行错误会自动恢复这些文件；掉电/进程强制退出时保留事务记录，先用回滚入口恢复，再重新更新。备份 ID 可通过 `ls -1 /opt/llm-bench/current/.code-updates/` 查找，再查看对应 `journal.json` 的状态。不要在事务执行期间启动栈或移动目录。

回滚前使用**当前版本**的 CLI 停止已启动的栈。然后从保留的代码包目录执行，备份 ID 使用应用成功时的输出：

```bash
bash repo/scripts/apply_code_update.sh /opt/llm-bench/current \
  --rollback '<备份ID>'
# 使用外部配置时，回滚也传入同样的 --config /path/site.yaml。
```

回滚恢复代码与校验清单，不恢复或删除测试结果和监控数据，也不会自动启动栈。再次启动按 4.4 节操作。只支持回滚最近一次尚未回滚的更新；多次更新需按逆序逐次回滚。更新后又修改了将被恢复的文件时，回滚会拒绝覆盖；先保留并处理这些本地改动。已有完整部署目录的手工迁移、依赖变化或镜像变化继续使用完整交付流程。

## YAML 迁移说明

`configs/` 中部署、交付、suite、search、环境、GPU/网络适配和 Dashboard 源配置均改为 `.yaml`；源码运行前先 `python3 -m pip install -r requirements.txt`。旧的外部 JSON 配置仍可读取，推荐改用 YAML；`create_site_config.py` 默认输出 `generated/site/site.yaml`。模板中的字符串若类似布尔值（如 `"off"`）或数字，请加引号；重复键会报错。

tokenizer 的 `tokenizer*.json`、ShareGPT/JSONL 数据集、运行状态/测试报告和 `references/` 中的上游原始资料保留原格式。Grafana 运行时仍需 JSON Dashboard，由 YAML 源自动渲染；Prometheus/Grafana provisioning 现在生成常规 YAML。无需手工修改 `storage.root/config/<哈希>/` 中的渲染文件。
